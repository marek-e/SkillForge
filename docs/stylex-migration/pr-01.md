## Layer order

`src/index.css` starts with

```css
@layer theme, base, priority1, priority2, priority3, priority4, priority5, priority6, priority7,
  priority8, components, utilities;
```

A `@layer` statement is allowed before `@import`, and layers are ordered by first declaration, so Tailwind's own `@layer theme, base, components, utilities;` (inside the `tailwindcss` import) can only reference layers that already exist. `priority1..priority8` are the layers `@stylexjs/unplugin` emits with `useCSSLayers` (one per property-priority bucket, at most eight).

The plugin is configured with the object form rather than `useCSSLayers: true`:

```ts
stylex.vite({
  useCSSLayers: { before: ['theme', 'base'], after: ['components', 'utilities'] },
})
```

`before`/`after` make StyleX repeat the full order in its own output (`@layer theme, base, priority1, …, components, utilities;`). That matters because the dev `<link>` the plugin injects is parsed **before** `index.css` (which Vite injects from JS), and without it the `priority*` layers would be declared first and would sit _below_ Tailwind's `base` until the runtime disabled the link. With it, the cascade is identical no matter which sheet the browser sees first — and the dev probe confirmed it: in one run the `__stylex_virtual__` style element was the first sheet in the document, in another the third, with identical computed styles.

**Final order, verified in the browser in both pipelines:**

`properties` (Tailwind) → `theme` → `base` → `priority1…priority8` (StyleX) → `components` → `utilities`

In the production bundle Tailwind's own lightningcss pass rewrites the statement from `index.css` into `@layer priority1,…,priority8,components;` placed directly between the `@layer base{…}` block and `@layer utilities{…}` (it drops the names it has already emitted as blocks), and the StyleX CSS appended at the end of the asset re-states `@layer theme, base, priority1;` / `@layer components, utilities;`, which is a no-op because every name already exists. Order preserved.

```css
  }
}

@layer priority4 {
  .x1q57ora { padding-top: .75rem; }
  .x5lhr3w { width: var(--x-width); }
  .x1u26ubr:is(*) svg { width: 2rem; }
}

@layer priority5 { .x8jarun[data-state="open"] { border-style: dashed; } }
@layer priority6 { .xvf591v[data-state="open"] { background-color: var(--accent); } }

@layer components, utilities;

@property --x-width { syntax: "*"; inherits: false }
```

Every selector form the migration plans to use compiles as [`conventions.md`](conventions.md) predicted, including the `:is(*) svg` descendant pass-through. The production build emits **one** CSS asset (`dist/assets/index-*.css`, 155 KB) with the StyleX rules appended after the whole Tailwind output; no separate `stylex.css` fallback file is produced.

The same 1.4 KB also lands in the build made **without** `VITE_VISUAL_GALLERY`, where Rollup drops the gallery chunk entirely. The unplugin collects rules while it transforms a module, not from the final module graph, so CSS for code the bundler later eliminates is not pruned. No shipped element carries those hashed classes, the whole 420-test suite passes against the frozen originals in both pipelines, and Tailwind already behaves the same way (it scans source files, so gallery-only utilities are in today's CSS too). `visual:check-gallery` proves the absence of gallery **code**, not of gallery CSS — worth remembering before assuming a later PR's dead StyleX styles disappear from the bundle.

## The dev-server trap (new finding)

`@stylexjs/unplugin`'s `handleHotUpdate` sends a `stylex:css-update` message on **any** watched file change, and its dev runtime answers every one of those with a `fetch('/virtual:stylex.css')`. Playwright streams its trace, screencast and result artifacts into `apps/ui/visual/results/`, which sits inside the Vite root — so during a visual test the page refetched the dev CSS roughly every 100 ms and `page.waitForLoadState('networkidle')` never resolved. The first full run after adding the plugin timed out on **every** one of the 424 tests, with 893 requests to `/virtual:stylex.css` in a single test's trace.

The fix is in `vite.config.ts`:

```ts
server: {
  watch: {
    ignored: ['**/visual/results/**', '**/visual/report/**', '**/test-results/**', '**/playwright-report/**'],
  },
}
```

Vite merges this with its own defaults. It affects the dev server only and nothing in the production build. Any later tooling that writes into the Vite root while a page is open will hit the same trap.
