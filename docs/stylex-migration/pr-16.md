## `buttonVariants` stays, and that decides the nav buttons

`calendar.tsx` is the only remaining caller of `buttonVariants` (`button.tsx` keeps it exported for
exactly this row). It still returns Tailwind utilities, so the four classes beside it on
`button_previous` / `button_next` — `size-(--cell-size) aria-disabled:opacity-50 p-0 select-none` —
**stay utilities too**: as StyleX they would sit in a `priorityN` layer and lose to
`buttonVariants`' own `h-8` and `px-2.5`. Both nav buttons therefore remain fully Tailwind, and
`buttonVariants` has exactly one call site (two uses) after this PR. It goes in PR 32.

The _day_ button is the opposite case: it is a real `Button`, so its rules move into the `sx` prop
and merge inside one `stylex.props` call instead of meeting as two class lists.

## What a `classNames` entry can and cannot become

Every entry of `DayPicker`'s `classNames` map is a class string on an element `react-day-picker`
renders, so a `stylex.props(...).className` can be passed there — but the modifier entries
(`range_start`, `range_middle`, `range_end`, `today`, `outside`, `disabled`) land on the **same**
day cell as `day`, added by a different map key. Two properties are written twice that way and can
never reach one `stylex.props` call:

| Property        | Contesting entries                                          | Tailwind's answer                                                                          |
| --------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `border-radius` | `day`, `range_start`, `range_middle`, `range_end`, `today`  | `.rounded-none` and the `-l-`/`-r-` longhands are emitted after `.rounded-(--cell-radius)` |
| `color`         | `today` (`text-foreground`), `outside`/`disabled` (`muted`) | `.text-muted-foreground` is emitted after `.text-foreground`                               |

A StyleX tie is not settled by the order the keys were written in (`conventions.md`, "Utility
source order decides a same-specificity tie"), so **those two families stay Tailwind classes** and
everything else in the map is StyleX. The radius is also why
`[&:last-child[data-selected=true]_button]:rounded-r-(--cell-radius)` stays: it reaches into the
`Button` inside the cell, whose radius is already StyleX, and has to keep outranking it.

## The day button's four properties

`CalendarDayButton` passes `styles.dayButton` through `Button`'s `sx`, which is applied last, so
three properties have to be **restated**: `borderRadius` would otherwise drop `Button`'s own
`rounded-lg`, and `backgroundColor` / `color` would drop the `ghost` variant's `hover:` and
`aria-expanded:` rules (`conventions.md`, "`stylex.props` merges a property whole").

The state keys are **bare** attribute selectors — `'[data-selected-single="true"]'` and the three
range ones — worth 5000 against a wrapped hover's 2330. That is what keeps a hovered selected day
on `--primary`, which is the order Tailwind gets from specificity ((0,2,0) utility against a
`priorityN` StyleX rule). `dark:hover:text-foreground` is the rule that has to beat _those_: it is
(0,3,0) today, so it stays in `utilities` rather than being nested under each state key.

`border-0` makes the border invisible, and the focus ring is written by
`group-data-[focused=true]/day:` from the **cell**, not by the button's own `:focus-visible`, so
`borderColor` and `boxShadow` are left to `Button` entirely and those two rules stay utilities.
`ring-ring/50 ring-[3px]` composes exactly the ring `Button` paints, measured live:
`… oklab(0.708 0 0 / 0.5) 0px 0px 0px 3px …`.

`size-auto w-full` both survive `twMerge` and `.w-full` is emitted after `.size-auto`, so the pair
is `width: 100%` with `height: auto`.

## Smaller things

- `**:[[cmdk-group-heading]]:*` becomes the descendant key `':is(*) [cmdk-group-heading]'`. The
  heading is rendered by cmdk **inside** the group this file owns and carries no class, so no
  utility can outrank it. The heading colour sits in the same object as the group's own `color`,
  because a property merges whole.
- The `SearchIcon`'s `size-4` moved to StyleX, which makes it start matching
  `InputGroupAddon`'s `[&>svg:not([class*='size-'])]:size-4`. Both ask for `1rem`, so the box is
  unchanged and the addon's copy simply wins from `utilities`.
- `text-sm` / `text-xs` are the paired line heights as the lengths they resolve to; the two
  `text-[0.8rem]` weekday/week-number rules write **only** a font size, because an arbitrary
  font-size utility leaves `line-height: var(--tw-leading)` invalid and the element inherits.
- `outline-hidden` is four longhands plus the `forced-colors` branch, as in `hover-card.tsx`.
- `p-1 pb-0` keeps Tailwind's own shorthand/longhand choice; `px-2`/`py-1.5` stay logical.

## Findings for conventions.md

Not applied here; `conventions.md` is the orchestrator's.

1. **A third-party `classNames` map is a merge boundary.** Entries that land on one element cannot
   share a `stylex.props` call, so any property two of them write has to stay Tailwind. Worth a row
   in the "whole-property merging" section, next to the `sx` case.
2. **A bare attribute key (5000) is the cheap way to outrank a wrapped hover (2330)** when a
   component's own state must beat a variant's `hover:` — and the rule that has to beat _it_ is then
   easiest left in `utilities`.
3. **A StyleX _value_ can be a Tailwind utility name**, not only a computed one: `borderCollapse:
'collapse'` adds `.collapse`. The existing note covers keywords in snapshots; this is the same
   trap in the source.
4. **`VISUAL_PORT` collides silently.** `reuseExistingServer` is true in dev mode, so a suite whose
   port is already held by another worktree runs happily against _that_ checkout and every test
   times out waiting for a section that does not exist there. Check the port before capturing.
