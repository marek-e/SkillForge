## Classes that stay Tailwind, and why

Cascade layers outrank specificity, so a StyleX rule in a `priorityN` layer loses to **any**
utility a caller puts on the same element — where `twMerge` used to delete only the base class with
the _same_ variant key. PR 04 met this for rules that reach a foreign child; this row met it for a
component's own declarations as well, and for a second mechanism: a Tailwind utility can write a
`--tw-*` custom property that another utility reads, which StyleX cannot reproduce at all.

Each file keeps the contested classes in one documented constant.

| `input.tsx`       | `dark:bg-input/30`, `disabled:bg-input/50`, `dark:disabled:bg-input/80`                                                                         | `sidebar.tsx`'s `SidebarInput` passes `bg-background`; as StyleX the dark background disappears in `sidebar-parts`                                         | PR 17          |
| `input.tsx`       | the five ring classes                                                                                                                           | the same caller's `shadow-none`, which used to lose to `focus-visible:ring-3`                                                                              | PR 17          |

## A paired line-height that has to stay a ratio

The first real casualty of writing a paired line-height as a length
([conventions](conventions.md#paired-line-heights-never-write-the-ratio) flagged this as a risk).

`InputGroupAddon` is `text-sm`, and both filter bars and the `input-group-search` gallery case put a
`<kbd class="text-[10px]">` inside it. `text-[10px]` compiles to
`font-size: 10px; line-height: var(--tw-leading)` with no fallback, so the line height is invalid at
computed-value time and the kbd **inherits** it. Tailwind's `text-sm` passes down the unitless
`calc(1.25 / 0.875)`, which the kbd resolves against its own 10px: 14.2857px. A StyleX
`lineHeight: '1.25rem'` passes down 20px instead, which grew the addon from 30.28px to 36px and
failed `computed-forms-controls-*.json` the first time.

Writing the ratio instead is not an option either: lightningcss folds it to five decimals, which
moves the addon's own line box off the 20px it has today. So `text-sm` stays a class on the addon.
Nothing else in this row has a descendant with a different font size, which is why nothing else
needed it.

## The layer statement had to grow

`src/index.css` declared `priority1..priority8`. The plugin emits **one layer per distinct
`Math.floor(priority / 1000)` bucket it has rules for**, named by position, and this row's
`::placeholder` and `::file-selector-button` rules are the first in the 8000/9000 range: the build
started emitting `priority9` and `priority10`.

A layer name that is not in the first `@layer` statement is appended **after** every declared layer,
so in the production bundle — where the StyleX CSS is parsed last — those two would have landed
after `utilities`, while in dev they would have landed in the right place. That is exactly the
dev/production split the statement exists to prevent. The statement now names ten, which is the
ceiling: a priority is a property priority (≤ 4000) plus 5000 for a pseudo-element plus a few
hundred for nested conditions, and the zero-priority bucket that holds `defineVars` counts as one.

## What the translation had to get right

Values come from [`tailwind-values.md`](tailwind-values.md); every declaration carries its original
class as a comment. Beyond the two items above:

- **Three margin rules on `FieldDescription`** are all (0,2,0), so Tailwind settles them by emission
  order in `@layer utilities`: `last:mt-0` (rule 683) → `nth-last-2:-mt-1` (966) →
  `[[data-variant=legend]+&]:-mt-1.5` (1193). StyleX's own priorities put `:last-child` (4054) and
  `:nth-last-child(2)` (4061) **above** `:is([data-variant="legend"]+*)` (4040), so the two
  combinations are written as nested conditions. The `field-legend-description` case pins it.
- **`has-data-checked:`** is one of `shadcn/tailwind.css`'s custom variants, not Tailwind's generic
  attribute syntax; the selector is copied from the built CSS rather than guessed
  (`:has(:where([data-state="checked"]), :where([data-checked]:not([data-checked="false"])))`).
- **`group-has-data-horizontal/field:text-balance`** compiles to a `:has()` that looks for a
  _descendant_ with `data-orientation`, so a horizontal `Field` never balances its own description.
  Copied as it is.
- **`@md/field-group:`** is a container query on `FieldGroup`, not on the viewport. It compiles:
  `'@container field-group (min-width: 28rem)'` is a valid StyleX condition key, worth +300 priority
  and a doubled class selector. `field-responsive-narrow` (320px) and `field-responsive-wide`
  (520px) capture both sides at a fixed viewport.
- **A dead rule is still a rule.** `FieldGroup`'s `data-[slot=checkbox-group]:gap-3` can never match
  (the element's own `data-slot` is `field-group`), and `InputGroupAddon`'s
  `group-data-[disabled=true]/input-group:opacity-50` has no writer for that attribute. Both are
  kept.
- **`p-2.5` on a child** is written as four longhands, because `stylex.props` merges shorthands and
  longhands differently; likewise `p-0` in the icon button sizes.
- **`InputGroupAddon`'s `pt-2` versus its base `py-1.5`** was measured rather than reasoned about
  (8px top, 6px bottom), and the base value is restated in the block variants, because a property
  is merged as a whole.

## The two control wrappers are unchanged

`InputGroupInput` and `InputGroupTextarea` keep their class strings byte for byte. Every class in
them is a plain utility that beats the component's own StyleX rule exactly the way it used to beat
the component's base class, and two of them (`dark:bg-transparent`, `dark:disabled:bg-transparent`)
are what `twMerge` uses to delete the background classes `Input` still carries. Rewriting them as
StyleX would change nothing and would lose that deletion.

## Built CSS

Production build compared against `6f90a39`:

- **Tailwind portion: one rule added, four removed.** Added: `.@container { container-type: inline-size }`,
  because `@container field-group (min-width: 28rem)` — the StyleX condition key — contains a
  string the Tailwind scanner reads as a utility. No element renders it, and it cannot be avoided
  without obfuscating the key. Removed: the four `has-[>[data-align=block-*]]:h-auto|flex-col`
  rules, whose only source was `InputGroup`'s class string; they are StyleX now and nothing else
  names them.
- Keeping `fieldVariants`, `inputGroupAddonVariants` and `inputGroupButtonVariants` byte-identical
  means Tailwind still emits every class they name, so no other rule was dropped even though no
  component calls them.
- **StyleX portion: 108 classes added, none removed.** Four rules look removed in a naive text
  diff; all four are selector groups that gained a member (StyleX merges identical declarations
  into one rule), and every class in them is still present with the same declaration.

## Observed pre-existing defects

Nothing was fixed. In addition to the lists in [`pr-00.md`](pr-00.md) and [`pr-04.md`](pr-04.md):

- **`md:text-sm` beats a caller's own text size above 48rem.** The skill name input is
  `text-2xl` and renders at 14px on desktop and 24px on mobile; three textareas are `text-xs` and
  render at 14px on desktop. Frozen as `quirk-input-caller-text-2xl` and
  `quirk-textarea-caller-text-xs`.
- **`FieldGroup`'s `data-[slot=checkbox-group]:gap-3` can never match**, because the element's own
  `data-slot` is `field-group`. Same for `InputGroupAddon`'s
  `group-data-[disabled=true]/input-group:opacity-50`: nothing writes that attribute.
- **`FieldTitle` renders `data-slot="field-label"`**, not `field-title`; the horizontal `Field` and
  the `FieldLabel` box both select on it, so it is load-bearing.
- **`group-has-data-horizontal/field:text-balance` never fires for the field's own orientation**
  (see above).
- **`[&>[role=checkbox],[role=radio]]:mt-px` is asymmetric**: it compiles to a child selector for
  `[role=checkbox]` and a descendant selector for `[role=radio]`.
