## The finding that mattered: `py-*`/`px-*` are **logical**, `pt-*`/`pr-*` are physical

`py-4` compiles to `padding-block`, `px-4` to `padding-inline`, while `pt-0`, `pb-0` and `pr-0`
compile to the physical longhands. Blink resolves a physical longhand over the logical property
that maps to it **whatever the source order**, so on a `Card`:

| Rule                                          | Position in the sheet   | Wins? |
| --------------------------------------------- | ----------------------- | ----- |
| `has-[>img:first-child]:pt-0` (`padding-top`) | earlier (offset 78 527) | yes   |
| `data-[size=sm]:py-3` (`padding-block`)       | later (offset 90 550)   | no    |

Both are (0,2,0), so pure cascade order says the size rule wins — and the first translation of
this row wrote it that way, giving a compact card with a leading image a 12px top padding where
Tailwind gives it none. `computed-data-display-extra-light.json` caught it on the
`card-sm-image-footer` case, to the pixel (248.25px against 260.25px).

The fix is not to hand-pick a winner but to **keep Tailwind's own choice of property**:
`paddingBlock` / `paddingInline` for the `py-*`/`px-*` half and the physical longhand for the
`pt-*`/`pb-*`/`pr-*` half. The same resolution then happens for the same reason, and the third
Tailwind rule (`data-[size=sm]:has-data-[slot=card-footer]:pb-0`) turns out to be redundant rather
than decisive. `TableHead` (`px-2` + `[&:has([role=checkbox])]:pr-0`) and `TableCell` (`p-2` +
`pr-0`) are written the same way.

## Rules that reach a `tr` stayed on the section

`[&_tr]:border-b` (head), `[&_tr:last-child]:border-0` (body) and `[&>tr]:last:border-b-0` (footer)
could have been re-expressed on `TableRow`, which this file owns and migrates in the same commit.
They were not, because the rendered result is only identical for a `tr` that **is** a `TableRow`: a
raw `<tr>` inside a `TableHeader` gets the border today and would stop getting it. Nothing renders a
raw `<tr>` right now, but the descendant keys cost nothing and keep every combination.

Two details make them work:

- **Longhands, not `border-width`.** `border-0` writes the shorthand, and a StyleX shorthand has a
  lower property priority than a longhand, so `borderWidth: 0` would have lost to `TableRow`'s own
  `borderBottomWidth: 1px` whatever the selector. All four widths and all four styles are written
  out, which is also exactly what `border-0` sets.
- **Specificity inside one layer.** `.body:is(*) tr:last-child` is (0,2,1) against `.row` (0,1,0),
  same property, same priority, same layer — so the section rule wins, as it does today.

## A selected row that is also hovered

`hover:bg-muted/50` (offset 64 018) and `data-[state=selected]:bg-muted` (offset 95 846) are both
(0,2,0) and Tailwind emits the selected rule later, so a selected row keeps its solid background
under the pointer. StyleX ranks a plain `:is()` at 2040 and a hover inside `@media (hover: hover)`
at 2330, which would have inverted it, so the combination is written as a nested condition — the
shape [`conventions.md`](conventions.md#utility-source-order-decides-a-same-specificity-tie)
prescribes. `state-table-row-selected-hover-{light,dark}.png` pins it in both themes and both
viewports.

## A new shape of the Tailwind-scanner trap

The scanner reads **every text file in the project, including the JSON snapshots the visual suite
writes**. A first version of the new computed-style dump tracked `display` over `thead`, `tbody`
and `tfoot`; their three computed values are also the names of three Tailwind display utilities, so
the build started emitting three rules no element uses. The three sections are now dumped on their
own, without that property — nothing is lost, because what they write is a border on their `tr`
children, which the row dump already pins.

Two plain comments leaked a utility the same way and were reworded (`collapse` in `card.tsx`,
`pr-0` in `table.tsx`). Four rows in a row have now hit this hazard in one form or another.

`transition-shadow`, and the 150 ms box-shadow transition raced the hover screenshot: one of the
four projects came out nine pixels different on a re-run. The transition is gone from the case (the
ring is what it is for) and its originals were recaptured. The other symptom in that first run — six
to nine corner pixels on the same case — turned out to be the padding bug above shifting the case
down the page, and disappeared with the fix.

## Observed pre-existing defects

Nothing was fixed. In addition to the lists in [`pr-00.md`](pr-00.md), [`pr-04.md`](pr-04.md),
[`pr-05.md`](pr-05.md) and [`pr-06.md`](pr-06.md):

- **`CardHeader`'s `[.border-b]` rules are dead.** No caller passes `border-b`, so the only thing
  the two rules do today is wait for one. Kept, and now pinned by two gallery cases.
- **`data-[size=sm]:has-data-[slot=card-footer]:pb-0` is redundant.** The unconditional
  `has-data-[slot=card-footer]:pb-0` already wins at the compact size, because it is a physical
  longhand and `data-[size=sm]:py-3` is not.
- **`TableHeader`'s `[&_tr]:border-b` is redundant too**: every `TableRow` already carries
  `border-b`.
- **A compact card with a leading image keeps its top padding on the bottom but not on the top** —
  the logical/physical asymmetry above is a quirk, not a design decision. `card-sm-image-footer`
  records it.
- **`Table`'s wrapper takes no `className`**, so a caller cannot reach the scroll container. Left
  as it is.
