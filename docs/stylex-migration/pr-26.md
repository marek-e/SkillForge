## Findings

- **Two breakpoints on one property are resolved by rewriting the earlier query, not by order.**
  `enableMediaQueryOrder` (on by default) applies `lastMediaQueryWinsTransform`, so the grid item's
  `@media (width >= 40rem)` ships as `@media (width >= 40rem) and (width <= 63.99rem)` while the
  64rem rule ships plain. The last key wins deterministically — but the exclusion is
  `not (width >= 64rem)` lowered to `<= 63.99rem`, so between 1023.84px and 1024px of viewport width
  **neither** rule matches and the item falls back to its `100%` default, where Tailwind's
  source-order cascade gave it `calc(50% - .5rem)`. No integer viewport width, hence no test and no
  unzoomed window, lands in that 0.16px band, and an explicit `and (width < 64rem)` lowers to the
  same `63.99rem`: the band is the toolchain's, not the style's. It is the migration's first
  two-breakpoint property, and the projects (1440, 390) cannot see the middle step at all.
- **`space-y-*` migrates when the route renders the children.** Tailwind's rule is
  `:where(.space-y-6 > :not(:last-child))`, (0,0,0) in `utilities`; the StyleX form is (0,2,0) in a
  `priorityN` layer. Both lose to any margin utility on a child, and none of `H1`, `Lead`,
  `Skeleton`, the `Card` inside `ToolCard` or the routes' own boxes declares one, so the 32px / 8px
  / 24px gaps hold. The compiler emits the pair as physical margins (PR 22).

## Observed pre-existing defects (nothing was fixed)

- **The grid centres its last row**: `justify-center` on a wrapping container leaves a trailing row
  of one or two cards centred under a full row (the last card sits at x=344 of a 592px row at 800px;
  pinned by `route-tools-populated-*`).
- **The detail route's title row never wraps**: `H1` is `text-4xl` beside a fixed 40px box in an
  `items-center` row with no `min-width`, so a long display name would overflow rather than wrap (no
  configured tool has one). `tools.tsx` pluralises the skill count but not `1 connected`.

## Findings for conventions.md

- **A property with two `@media` keys is rewritten, not just ordered.** `enableMediaQueryOrder`
  negates every later query out of the earlier ones so the last key wins; lightningcss then lowers
  `not (width >= 64rem)` to `(width <= 63.99rem)`, leaving a 0.16px band where neither branch
  matches and `default` applies. A `sm:`/`lg:` pair is not a plain "later rule wins" translation.
- **The screenshot matrix has exactly two widths**, so any step between 640px and 1023px is
  invisible to it — and to a gallery case, captured in the same two viewports. A row migrating one
  needs a computed-style probe at those widths on the clean base before it edits anything.
