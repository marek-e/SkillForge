## The correction commit

`d3f8a3d` — _"fix(ui): wrap StyleX hover rules in the hover media query Tailwind emits"_.

PR 04 read the shipped CSS wrongly and wrote its hover rules as a bare `':hover'`. PR 06 corrected
the documentation but not the four files. All 25 of their hover rules are now wrapped, including
the eight arbitrary-variant ones in `badge.tsx`, whose Tailwind form is
`&:is(a):hover { @media (hover: hover) { … } }`.

**Proving it needed a pointer that cannot hover, and that is not a media emulation.** Chromium
reports `hover: hover` in both viewport projects, so no existing screenshot could see the
difference, and `Emulation.setEmulatedMedia` does not help either: Blink's media-feature overrides
have no `hover` entry, so the call is accepted and silently ignored — measured, not assumed.
What moves it is `Emulation.setTouchEmulationEnabled`, which makes `DevToolsEmulator` set the
primary hover type to none and the primary pointer type to coarse while the mouse keeps working.
That is `emulateNoHover` in `visual/helpers.ts`.

`visual/hover-media.spec.ts` is a new spec with 20 originals captured from the frozen tree: five
hover targets (a default `Button`, a `Toggle`, an anchor `Badge` in two variants and the inactive
half of `DisplayViewSwitch`) hovered under that emulation, in both themes and both viewports.
Measured on the three trees:

| Tree                              | Result                   |
| --------------------------------- | ------------------------ |
| frozen (`ee0f797`, pure Tailwind) | passes — the originals   |
| PR 04's bare `':hover'`           | **fails by 2106 pixels** |
| wrapped                           | passes                   |

The wrapper also **raises the rule's priority**, from 2130 to 2330 in `conventions.md`'s table, so
it has to be added at every level of a nested condition at once: a `':is(.dark *)'` branch whose
`':hover'` stayed bare would drop below the plain hover's new 2330 and stop winning. Every nested
hover in the four files was wrapped in the same pass, which is what the three dark-mode cases
(`badge-hover-ghost`, the outline button, the destructive button) depend on.

## The finding that mattered: a paired `text-*` is contested here too, and the first probe missed it

Four containers in this row carry `text-sm`: `TabsTrigger`, `TabsContent`, `AccordionTrigger` and
the accordion body. All four hold content the caller supplies, so all four are exposed to the trap
[`conventions.md`](conventions.md#paired-line-heights-never-write-the-ratio) records: Tailwind
passes the **ratio** `calc(1.25 / 0.875)` down to a descendant that has a font size of its own and
no line height, while a StyleX `1.25rem` passes a **length**.

The first version of the two probe cases put a `Button size="sm"` inside the trigger and the
panel, and **passed** — because a button has a fixed height, so its inherited line height changes
nothing that a screenshot can see. The second version puts a ten-pixel span in a place that is
sized by its content, and the difference appeared immediately:

| Element                                      | Tailwind    | first StyleX translation |
| -------------------------------------------- | ----------- | ------------------------ |
| vertical `TabsTrigger` holding a 10px span   | `20.2812px` | `26px`                   |
| whole vertical `Tabs` (list and panel agree) | `52.2812px` | `58px`                   |
| `AccordionTrigger` holding a 10px span       | `38px`      | `42px`                   |
| accordion body holding a 10px paragraph      | `68.2812px` | `74px`                   |

10px × `calc(1.25 / 0.875)` is 14.2812px; 10px under a 20px length is 20px. All four `text-sm`
classes therefore **stay Tailwind**, and the two `*-inherited-leading` cases stay in the gallery to
keep them honest. The lesson is in `conventions.md`: a probe for this trap has to sit where the
inherited line box actually sizes a box.

## What the translation had to get right

Values come from [`tailwind-values.md`](tailwind-values.md) and, for every rule in this row, from
the **built CSS asset** rather than from the table — each utility was looked up in
`dist/assets/*.css` before it was translated. Six things are worth calling out.

### 1. Three rules write the tab trigger's `box-shadow`, and they compose rather than compete

The focus ring, the active shadow of a `default` list and the shadow reset of a `line` list all
re-declare the five-layer chain, but they fill **different slots** through different `--tw-*`
variables, so a focused active trigger gets the ring _and_ the shadow. Reading the built CSS as if
one rule beat the other would have produced a trigger with only one of them. The four combinations
are written out as nested conditions:

| State                               | Composed value                          |
| ----------------------------------- | --------------------------------------- |
| focus-visible, inactive             | ring in slot 4                          |
| active in a `default` list          | the two `shadow-sm` layers in slot 5    |
| active in a `default` list, focused | **both**                                |
| active in a `line` list, focused    | ring only, because the reset is a no-op |

### 2. `data-active:` wraps its selector in `:where()`, which costs it a specificity point

`data-active:bg-background` compiles to `.x:where([data-state="active"])` — (0,1,0) — while
`group-data-[variant=line]/tabs-list:bg-transparent` is (0,2,0). So a trigger inside a `line` list
is transparent **whether it is active or not**, and the active rule never gets a turn. Every
combination of the two is written out rather than left to the order two same-priority StyleX rules
happen to be emitted in.

The same `:where()` is why `dark:data-active:border-input` (0,2,0) beats
`focus-visible:border-ring` (0,2,0) by emission order, and why the line list's
`dark:…:data-active:border-transparent` (0,3,0) beats both.

### 3. `after:` always writes `content`, and where it writes it decides whether the pseudo exists

Tailwind's `after:` variant emits `content: var(--tw-content)` in **every** rule it generates, and
`--tw-content` is registered with an initial value of `""`. So:

- the tab trigger's indicator is generated on every trigger, and only `opacity` tells the active
  one apart;
- the resize handle's hit area is generated on every handle;
- the accordion trigger's `::after` is generated **only while it is focus-visible**, because the
  only rule that mentions it is the focus one. It then joins the trigger's `justify-between` flex
  row as a zero-width item. The border colour it is given never paints, because nothing gives the
  pseudo-element a border width. Both halves are reproduced as found and
  `state-accordion-focus-*.png` pins them.

StyleX puts the pseudo-class before the pseudo-element when a condition is nested inside a
`'::after'` object, so `content: { default: null, ':focus-visible': '""' }` compiles to
`.x:focus-visible::after`. Verified against the frozen `::after` dumps, which match to the pixel.

### 4. Two descendant rules moved onto the element they style, one stayed where it was

| Rule                                                | Decision                                                                                                                                                              |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the accordion trigger's three chevron rules (`**:`) | **moved onto the chevrons**, which this file renders. No caller can reach them, so nothing can outrank the StyleX rule, and the computed result is identical          |
| the two chevron visibility rules                    | same, expressed as `':is(.group\/accordion-trigger[aria-expanded="true"] *)'` on each icon                                                                            |
| the resize handle's grip rotation                   | **kept as a descendant key on the handle** (`':is([aria-orientation="horizontal"])>div'`), because that is the child selector Tailwind emits and the `<div>` is owned |

### 5. `outline-none` poisons a later `outline-*` on the same element

The scroll-area viewport has both `outline-none` and a focus `outline-1`. The first sets
`--tw-outline-style: none` **and** `outline-style: none`; the second writes
`outline-style: var(--tw-outline-style)`, which therefore resolves back to `none`. The viewport
never grows an outline in either state, and only the width it also sets is observable at all. The
StyleX version writes `outlineStyle: 'none'` unconditionally and the width behind the focus
condition, which is the same computed pair.

The tab trigger is the opposite case: it has **no** `outline-none`, so its focus `outline-1`
resolves `--tw-outline-style` to its registered initial `solid` and the outline does paint.

### 6. Smaller things

- `flex-1` is `flex: 1` in Tailwind v4, which computes to `1 1 0%`.
- `-translate-x-1/2` goes through the `translate` property, not `transform`, and the unset axis has
  a registered initial value of `0` — so the pair is `-50% 0`, which Chrome serialises as `-50%`.
- `rounded-full` is `calc(infinity * 1px)`, which computes to `3.35544e+07px`.
- `data-horizontal:` / `data-vertical:` on the scrollbar and `data-active:` on the trigger are
  `shadcn/tailwind.css` custom variants; `data-[variant=line]:` on the list is a plain attribute
  selector on the element itself.
- shadcn's `accordion-down` / `accordion-up` keyframes win over `tw-animate-css`'s, and the height
  expression in the shipped asset is
  `var(--radix-accordion-content-height, var(--accordion-panel-height, auto))` — a shorter fallback
  chain than either document describes.
- The accordion animation is `0.2s ease-out`, one iteration, `normal`, fill mode `none`, delay
  `0s`; all six longhands are written out, because the utility is a shorthand and a shorthand also
  resets what it does not name.

## The scanner trap in a new shape: a keyword the migration must emit

Four rows in a row have now hit Tailwind's source scanner. This one is the first shape that
**cannot be reworded away**: the accordion's timing function is the CSS keyword `ease-out`, which
is also the name of a Tailwind utility. Chrome does not serialise the equivalent `cubic-bezier()`
back to the keyword (measured), so the component has to contain the literal string — and so does
the JSON snapshot that records the computed value. The build therefore gains:

- `.ease-out { --tw-ease: var(--ease-out); transition-timing-function: var(--ease-out) }`, which no
  element renders, and
- an `--ease-out` entry in the `@theme` token block on `:root, :host`, which nothing reads.

Neither changes a rendered pixel — the whole suite passes — and both disappear with the utility
layer in PR 32. Three other leaks in this row **were** reworded: two utility names in a doc comment
that made the build emit the accordion animation classes, the collapsible keyframe names, and the
word "resize" in a test comment, which is a utility on its own.

## Observed pre-existing defects

Nothing was fixed. In addition to the lists in [`pr-00.md`](pr-00.md), [`pr-04.md`](pr-04.md),
[`pr-05.md`](pr-05.md), [`pr-06.md`](pr-06.md), [`pr-07.md`](pr-07.md) and [`pr-08.md`](pr-08.md):

- **`ResizablePanelGroup` ignores every class it sets, and every class a caller passes for the same
  properties.** `react-resizable-panels` writes its own inline `style` with `display`,
  `flex-direction`, `width` and `height`, and an inline style beats any class. That is why an
  `h-40` on a panel group renders 46px tall (horizontal) or 3px tall (vertical) in the `disclosure`
  section, while the same class on a `ScrollArea` next to it renders 160px.
- **`ring-offset-background` on the resize handle paints nothing.** It sets
  `--tw-ring-offset-color`, which only the ring-offset shadow layer reads, and nothing sets a ring
  offset _width_, so that layer stays at `0 0 #0000`.
- **The scroll-area viewport can never show its focus outline**, because `outline-none` sets the
  variable the focus rule reads (see above). The three-pixel ring next to it does paint.
- **The accordion trigger grows a generated `::after` while it is focused**, which becomes a
  zero-width flex item in a `justify-between` row, and gives it a border colour it can never show.
- **A vertical `Tabs` never reaches Radix.** `Tabs` destructures `orientation` for its own
  `data-orientation` attribute instead of forwarding it, so Radix's context stays horizontal: every
  trigger is emitted with `data-orientation="horizontal"` and arrow-key navigation stays on the
  horizontal axis even though the list is stacked. The layout rules key off the _root's_ attribute
  and are unaffected.
- **`animation sheet-right-open dark` flaked once, at the 0 ms frame, in the mobile project.**
  Cause, measured from the diff: the trigger keeps the pointer after `locator.click()`, so its
  150 ms hover transition is running, and `installAnimationFreeze` pauses animations but not
  transitions. `freezeAnimationsAt` seeks the transition to 0 ms **if it still exists**; under full
  suite load it can finish first, and the button is then captured hovered. Five isolated re-runs
  and three more full runs were clean. It belongs to `sheet` (PR 11) rather than to this row, the
  original was not touched, and the fix is not free: moving the pointer away would break the
  accordion frames, whose originals were captured with the trigger underlined by hover.
