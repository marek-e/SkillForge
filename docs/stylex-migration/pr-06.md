## Two classes stay, and they carry no styling

`peer` (on `Checkbox`, `RadioGroupItem` and `Switch`) and `group/radio-group-item` are literal
class names other rules select through: `Label`'s `peer-disabled:opacity-50` /
`peer-disabled:cursor-not-allowed` (StyleX since PR 05, still matching `.peer:disabled ~ *`) and the
radio indicator's `group-aria-invalid/radio-group-item:text-destructive`. `group/switch` is kept
too, although nothing selects through it any more — the thumb now takes its size directly.

## What the translation had to get right

### `hover:` **is** wrapped in a media query

PR 04 recorded the opposite, and [`conventions.md`](conventions.md) and
[`tailwind-values.md`](tailwind-values.md) §9 were changed to match it. Both are corrected back
here, because the shipped CSS asset of this project contains **nine** `@media (hover: hover)`
blocks, and **every** `hover:` utility in the bundle is inside one — all 31 of them, including
`hover:bg-muted`, `hover:bg-primary/80`, `hover:underline`, `dark:hover:bg-blue-500/25` and
`[a]:hover:bg-destructive/20`. (A `:hover` written inside an _arbitrary_ selector, such as
`[&>a:hover]:text-primary`, is not wrapped — that is the one shape that really is bare.)

The earlier measurement was almost certainly a line-based `grep -c` on a single-line minified
asset, which reports `1` however many blocks there are.

The slider thumb's `hover:ring-3` is therefore written as
`'@media (hover: hover)': { default: null, ':hover': … }`. **`button.tsx`, `badge.tsx`,
`toggle.tsx` and `display-view-switch.tsx` still have theirs written bare** and now apply their
hover styling on pointers that cannot hover, where Tailwind would not. No screenshot can catch it:
Chromium reports `hover: hover` in both viewport projects. It needs its own change; this row does
not touch PR 04's files.

### StyleX gives most conditions the same priority

Measured with the compiler, for a property whose base priority is 2000:

| Key                                                     | Priority |
| ------------------------------------------------------- | -------- |
| `default`                                               | 2000     |
| `':is(…)'`, `':focus-visible'`                          | 2040     |
| `':hover'`                                              | 2130     |
| `':active'`                                             | 2170     |
| `'@media (hover: hover)'` + `':hover'`                  | 2330     |
| a bare attribute key such as `'[data-state="checked"]'` | 5000     |
| every extra nesting level                               | +40 each |

So `:is(…)` and `:focus-visible` tie, and a tie is **not** resolved by the order the keys appear in
`stylex.create`: identical declarations are deduplicated across the whole app, so a rule's position
in the sheet is where the _first_ module that emitted that exact declaration put it. The checkbox
proved it — a checked, focused checkbox came out `--primary` instead of `--ring`, because
`borderColor: { ':focus-visible': colors.ring }` had already been emitted by `button.tsx`, early.

`Checkbox`'s border colour is written as a full decision tree for that reason: six Tailwind rules
that resolve by specificity (`dark:aria-invalid:` > `aria-invalid:aria-checked:` >
`aria-invalid:` > `focus-visible:` > `data-checked:` > `border-input`) become a nested structure
where each combination is one level deeper than the rules it has to beat.

### The custom `data-*` variants

`data-checked:`, `data-unchecked:`, `data-disabled:`, `data-horizontal:` and `data-vertical:` are
`shadcn/tailwind.css` custom variants, not Tailwind's generic attribute syntax. Each compiles to a
pair of `:where()` selectors, copied from the built CSS into one constant per file — which also
records that `data-checked:` matches `data-state="checked"` but **not**
`data-state="indeterminate"`, so an indeterminate checkbox keeps the unchecked background and
border while still showing the indicator.

### The switch thumb no longer reads its size off an ancestor

`group-data-[size=default]/switch:size-4` and the two
`group-data-[size=…]/switch:data-checked:translate-x-[calc(100%-2px)]` rules asked the root for the
size. `Switch` renders the thumb itself, so the size variant now picks the thumb style directly and
only the thumb's own `data-state` stays a condition. Same computed `translate`, same box, two fewer
Tailwind rules in the bundle.

### The invisible hit areas

All three of `after:absolute after:-inset-x-3 after:-inset-y-2` (checkbox, radio item, switch) and
`after:-inset-2` (slider thumb) become a `'::after'` key with `content: '""'` — Tailwind's `after:`
variant emits `content: var(--tw-content)`, whose registered initial value is the empty string. The
live probe compares `content`, `position`, the four inset sides and `width` of `::after` on every
element, so the pointer targets are verified, not assumed.

### Smaller things

- `rounded-full` is `calc(infinity * 1px)`, not a large literal.
- `bg-white` is `#fff`; it is not a project token.
- `focus-visible:outline-hidden` keeps its `@media (forced-colors: active)` half, where Tailwind
  restores a transparent 2px outline.
- `Slider`'s `disabled:pointer-events-none disabled:opacity-50` sit on a Radix `span`, so `:disabled`
  can never match them. Kept as they are.
- `transition-transform` is `transform, translate, scale, rotate`;
  `transition-[color,box-shadow]` is `color, box-shadow`.

## A PR 05 defect this row's cases caught

`checkbox-in-disabled-field` renders a disabled `Checkbox` next to a `FieldLabel`, which is a
`Label` — and `Label`'s `peer-disabled:opacity-50` used to dim it. PR 05 gave `FieldLabel` an `sx`
that declares `opacity` for `group-data-[disabled=true]/field:`, and `stylex.props` merges a
property **as a whole**, so that `sx` silently replaced `Label`'s two `opacity` conditions instead
of adding to them. The label stopped dimming.

No PR 05 case put a disabled peer next to a `FieldLabel`, so nothing caught it there. `field.tsx`
now restates both of `Label`'s conditions, and the case pins it in both themes and both viewports.
It is the same trap [`conventions.md`](conventions.md#stylexprops-merges-a-property-whole) already
records, in a new place: **an `sx` prop is subject to it too**, and that is now written down.

## Observed pre-existing defects

Nothing was fixed. In addition to the lists in [`pr-00.md`](pr-00.md), [`pr-04.md`](pr-04.md) and
[`pr-05.md`](pr-05.md):

- **`data-checked:` does not match an indeterminate checkbox**, so
  `checkbox-invalid-indeterminate` and `checkbox-indeterminate-disabled` show the indicator on an
  unchecked-looking box.
- **A checked checkbox loses its primary border as soon as it is focused**, because
  `focus-visible:border-ring` is (0,2,0) and `data-checked:border-primary` is (0,1,0).
- **`Slider`'s thumb carries `disabled:` rules that can never match** (Radix renders a `span`), so
  a disabled slider dims only through the root's `data-disabled:opacity-50`.
- **`Switch`'s `group/switch` class no longer has a selector**, and `RadioGroupItem`'s
  `aspect-square` is redundant next to `size-4`. Both are kept.
