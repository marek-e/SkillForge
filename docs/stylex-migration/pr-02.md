## The token module

`src/styles/tokens.stylex.ts`. The file name is not cosmetic: `defineVars`/`defineConsts` may
only appear in a `*.stylex.ts` file, and the compiler resolves them through the **import path**,
so consumers must import from here and never re-export.

```ts
import { colors, fonts, motion, radius } from '@/styles/tokens.stylex'
```

| Export   | Mechanism      | Contents                                                                                                               |
| -------- | -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `colors` | `defineVars`   | 32 entries, `background` … `toasterBackground`, each aliasing one project custom property (`'var(--background)'`, …)   |
| `radius` | `defineConsts` | `base`, `sm`, `md`, `lg`, `xl`, `2xl`, `3xl`, `4xl` — the exact `calc(var(--radius) ± Npx)` strings of `@theme inline` |
| `fonts`  | `defineConsts` | `sans`, `serif` (project overrides), `mono` (Tailwind's unoverridden `--font-mono` stack)                              |
| `motion` | `defineConsts` | `duration: '150ms'`, `ease: 'cubic-bezier(0.4, 0, 0.2, 1)'` — Tailwind's `--default-transition-*`                      |

**Why `defineVars` for colours and `defineConsts` for the rest.** `defineVars` emits a real
custom property per entry (`:root { --x8vbio4: var(--background); … }`) and `colors.background`
compiles to `var(--x8vbio4)`. That indirection is what lets the palette stay themable by StyleX
later, and it resolves correctly because `.dark` sits on `<html>` — which _is_ `:root` — so
`--x8vbio4` is already the dark value by the time it inherits. `defineConsts` emits nothing: the
compiler inlines the literal at each use site, so `borderRadius: radius.md` compiles to
`border-radius: calc(var(--radius) - 2px)`, character for character what `rounded-md` produces.
That is the right tool for anything that is already a literal, and it keeps the stylesheet from
growing.

`.dark` itself stays in CSS. `defineVars` has no selector-scoped values and a `':where(.dark)'`
key compiles to invalid nested CSS, so the `:root`/`.dark` blocks keep doing the switching and
`next-themes` is untouched — exactly as [`conventions.md`](conventions.md) predicted.

An `xs` radius step is deliberately missing: the project does not override Tailwind's
extra-small radius, so the two styles that want it keep the `0.125rem` literal locally.

## The global stylesheet

`src/index.css` keeps the layer statement first (a `@layer` statement is allowed before
`@import`), then the five package imports, then `@import './styles/global.css'`,
`@custom-variant dark` and `@theme inline`. `@theme inline` stays until PR 32, because Tailwind
utilities still resolve `--color-*` / `--radius-*` / `--font-*` through it.

The import sits **after** the font imports, which is precisely where the project's own blocks
used to sit inline, so the emitted order of the unlayered rules is unchanged:
`@property` (tw-animate) → `@font-face` (fontsource) → `:root` → `.dark` → `.drag` → `.no-drag`
→ the three `.electron-app` rules.

`global.css` holds, in this order:

1. `:root { … }` and `.dark { … }` — copied verbatim.
2. `@layer base { … }` — the same three rules, with the `@apply`s written out.
3. `.drag`, `.no-drag` — **not ported.** Comment names PR 20 (`electron-titlebar`, `Layout`),
   which owns the elements that carry those classes.
4. `.electron-app [data-slot='sidebar-container' | 'sidebar-wrapper' | 'sidebar-rail']` — **not
   ported.** Comment names PR 17 (`sidebar`), where they become `':is(.electron-app *)'` keys on
   the three slots' own styles. Porting them now would mean editing `components/ui/sidebar.tsx`.

### The `@apply` expansion, and the `@supports` trap

The compiled form, from the real build and from
[`tailwind-values.md` §11](tailwind-values.md):

```css
@layer base {
  * {
    border-color: var(--border);
    outline-color: var(--ring);
  }
  @supports (color: color-mix(in lab, red, red)) {
    * {
      outline-color: color-mix(in oklab, var(--ring) 50%, transparent);
    }
  }
  body {
    background-color: var(--background);
    color: var(--foreground);
    font-family:
      Geist Variable,
      sans-serif;
  }
  html {
    font-family:
      Geist Variable,
      sans-serif;
  }
}
```

The `@supports` pair is **not** authored. `outline-color` is written once, as the bare
`color-mix()`; lightningcss (inside `@tailwindcss/vite`) is what splits it into the
`var(--ring)` fallback plus the guarded `color-mix()`, in both the dev server and the production
bundle. Two other spellings were tried and rejected because both produce a _second_, redundant
guard nested inside the first (+73 bytes, same computed value):

| Authored form                                         | Emitted                                                        |
| ----------------------------------------------------- | -------------------------------------------------------------- |
| `outline-color: color-mix(in oklab, …)` — **shipped** | `*{…var(--ring)}` + one `@supports` — byte-identical to `main` |
| nested `@supports` inside the `*` rule                | one extra `@supports` level                                    |
| sibling `@supports` block                             | one extra `@supports` level                                    |

The `@layer base` wrapper is kept. It is what keeps these rules below every StyleX `priorityN`
layer and below Tailwind utilities; unlayered, they would beat both.

which writes two JSON originals per run — 8 JSON originals:

- `computed-tokens-*.json` — `<html>` class, all 33 project custom properties resolved through a
  probe element, and the resolved `background-color` / `color` / `border-radius` / `font-family`
  / `transition-*` of every token element, i.e. the whole chain
  StyleX var → project custom property → `:root`/`.dark` value.
- `computed-native-defaults-*.json` — `font-family`, `font-size`, `line-height`, `color`,

to `oklch(100% 0 0)` and `0.625rem` to `.625rem` when it minifies the production bundle, while
the value the browser resolves is identical. `--radius` is probed as a width (`10px`),
everything else as a colour.

## Built CSS diff

`apps/ui/dist/assets/index-*.css`: **154 578 → 157 761 bytes, +3 183**. Top-level structure and
order are unchanged; every byte is accounted for.

| Block                                                                  |                 Δ bytes | Why                                                    |
| ---------------------------------------------------------------------- | ----------------------: | ------------------------------------------------------ | --------------- | -------- | ---------------------------------------------------------------------------- |
| `@layer properties`, `@layer theme`, `@layer base`, `@font-face` ×5    |                       0 | byte-identical                                         |
| `:root`, `.dark`, `.drag`, `.no-drag`, the three `.electron-app` rules |                       0 | byte-identical, same position, each still exactly once |
| `@layer utilities`                                                     |                **+253** | one new rule, `.ring { … }` — see below                |
| `@layer priority2` / `3` / `4` (StyleX)                                | **+355 / +1063 / +144** | the `tokens` gallery section's compiled styles         |
| `@property --x-backgroundColor                                         |        --x-borderRadius | --x-color                                              | --x-fontFamily` | **+254** | the four dynamic styles the section uses to render one rule per token family |
| `:root, .x13qknre { --x8vbio4: var(--background); … }`                 |               **+1114** | the `defineVars` aliases, 32 declarations              |

**The `.ring` rule.** Tailwind v4 scans every source file for class-like strings, including
`.ts` files and including comments. `ring: 'var(--ring)'` in `tokens.stylex.ts` is enough for it
to emit `.ring { --tw-ring-shadow: …; box-shadow: … }`, which did not exist before because no
element uses the bare `ring` utility. It still does not: the rule is inert and disappears with
Tailwind in PR 32. The same mechanism first added `--radius-xs: .125rem` to `@layer theme`
because a comment in the token module spelled out `rounded-xs`; the comment was reworded and the
theme layer is byte-identical again. **Watch for this in every later PR**: a Tailwind-shaped
string anywhere in a migrated file, even inside a comment, grows the utility layer.

**The StyleX rules ship even though the gallery does not.** Confirmed again here: the 1.9 KB of
`tokens`-section rules and the `defineVars` block are in the build made _without_
`VITE_VISUAL_GALLERY`, because the unplugin collects CSS at transform time, not from the final
module graph (see [`pr-01.md`](pr-01.md)). `visual:check-gallery` still passes — it proves the
absence of gallery _code_, not of gallery CSS.

## The `@` alias trap

The StyleX compiler resolves `defineVars`/`defineConsts` imports with its own resolver, which
knows nothing about Vite's `resolve.alias`. `import … from '@/styles/tokens.stylex'` therefore
failed every transform with _"Could not resolve the path to the imported file"_ until
`vite.config.ts` grew:

```ts
unstable_moduleResolution: { type: 'commonJS', rootDir: __dirname },
aliases: { '@/*': [path.resolve(__dirname, 'src', '*')] },
```

`rootDir` is pinned rather than left at its `process.cwd()` default so the hashed variable names
do not depend on the directory the command was run from (`pnpm visual` runs from the repo root,
`pnpm --filter @skillforge/ui build` from `apps/ui`). Neither option changes the compiled output
of `stylex.create`; the canary's rules are byte-identical.
