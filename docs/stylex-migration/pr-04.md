## What the translation had to get right

Values come from [`tailwind-values.md`](tailwind-values.md) §1 (spacing), §3 (type), §4
(`color-mix` opacity), §5 (`border`, `rounded`, `ring`), §6 (`shadow`), §7 (layout), §8
(transitions) and §9 (variants). Each declaration carries its original class as a comment. Five
things are worth calling out, each of which broke a comparison first:

### 1. `hover:` is not wrapped in `@media (hover: hover)`

`tailwind-values.md` §9 and the mapping table in `conventions.md` both claimed
`&:hover { @media (hover: hover) { … } }`. The shipped CSS asset of this project contains
**no** Tailwind rule inside such a media query: it emits `.hover\:bg-muted:hover { … }`, and the
same for `dark:hover:` and `[a]:hover:`. Both documents are corrected; the components use plain
`':hover'`. (PR 01's canary keeps its media nesting on purpose — it probes the syntax, it does
not mirror a Tailwind rule.)

### 2. The composed `box-shadow`, not a flattened ring

`focus-visible:ring-3` re-declares the five-slot chain and leaves four slots at `0 0 #0000`. The
styles write all five out, so the computed string is identical:

```ts
':focus-visible':
  '0 0 #0000, 0 0 #0000, 0 0 #0000, 0 0 0 3px color-mix(in oklab, var(--ring) 50%, transparent), 0 0 #0000',
```

**No computed-style snapshot needed the documented textual exception.** A flattened single-layer
shadow would have needed one; this does not.

### 3. Which of two same-specificity variants wins

`.x:hover`, `.x[aria-expanded="true"]`, `.x:focus-visible` and `.x[aria-invalid="true"]` are all
(0,2,0), so Tailwind settles them by emission order in `@layer utilities`. Read off the built CSS
(later wins): `hover:` → `aria-expanded:` → `focus-visible:` → `aria-invalid:` → every `dark:*`.

StyleX orders by its own per-condition priority, which is not the same, so the three combinations
where the two rules **disagree** are written as nested conditions:

| Combination                         | Correct value                                                                    | Written as                                                   |
| ----------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `aria-invalid` + `focus-visible`    | the invalid colour and the destructive ring                                      | `':is([aria-invalid="true"])': { ':focus-visible': … }`      |
| `secondary` `aria-expanded` + hover | the solid secondary background                                                   | `':is([aria-expanded="true"])': { ':hover': … }`             |
| dark `outline` `aria-expanded`      | `input/30`, because `dark:bg-input/30` is emitted after `aria-expanded:bg-muted` | a `':is([aria-expanded="true"])'` key inside the dark branch |

and one combination is written **flat on purpose**: light `outline` `aria-expanded` + hover, where
both rules set `muted`. Nesting it produced an `[aria-expanded]:hover` rule that also outranked
`dark:hover:bg-input/50`, which cost four dark screenshots (collapsible, popover, calendar popover,
mode-toggle menu — all of them an expanded outline trigger under the pointer that clicked it).

Two more measured, now explicit: in dark a focused `outline` button keeps `dark:border-input`
rather than `focus-visible:border-ring`, and an expanded one keeps `dark:bg-input/30`.

### 4. `stylex.props` merges a property whole

A variant that sets `borderColor` drops the base's `':focus-visible'` and `aria-invalid` border
rules with it, and a size that sets `height` drops a base `height` whose only declaration was the
icon rule. So every variant restates the focus/invalid border and ring, and the icon sizing left
`base` entirely.

### 5. Arbitrary type sizes and the radius `min()`

`text-[0.8rem]` (button `sm`, toggle `sm`) has no paired line-height: Tailwind emits
`line-height: var(--tw-leading)`, `--tw-leading` is registered with no initial value, so the
declaration is invalid at computed-value time and the property falls back to `inherit`. Written
as `lineHeight: 'inherit'`, which reproduces the measured 19.2px.
`rounded-[min(var(--radius-md),Npx)]` becomes `min(calc(var(--radius) - 2px), Npx)` — the
project's own `calc()`, never the Tailwind-generated `--radius-md`. Computed value verified equal
(8px for both the 10px and the 12px forms).

## Descendant rules that stayed Tailwind

Cascade layers outrank specificity, so a StyleX rule in `priorityN` loses to **any** utility on
the element it targets. That is right for the component's own box and wrong for a rule that
reaches out to an element the component does not own. Four such rules are kept as literal
Tailwind classes in the bridge, each with a comment naming the PR that removes it:

| Rule                                                      | Where                       | Proof it is contested                                                                                         |
| --------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `[&_svg:not([class*='size-'])]:size-{3,3.5,4}` (per size) | `Button`                    | `mode-toggle.tsx` renders `<Sun className="h-[1.2rem] w-[1.2rem]" />`; as StyleX it rendered 19.2px, not 16px |
| `[&>svg]:size-3!`                                         | `Badge`                     | the `!important` exists precisely to beat a caller's `size-*`, which StyleX cannot express                    |
| `[&_svg:not([class*='size-'])]:size-4`                    | `Toggle`, `ButtonGroupText` | same shape, kept for consistency with `Button`                                                                |
| the eleven `[&>*…]` / `*:` child rules                    | `ButtonGroup`               | `Input`'s own `rounded-lg`/`border` and `SelectTrigger`'s `rounded-lg` beat a StyleX rule on the group        |

`twMerge` still lets a caller override them, exactly as before, because they merge on the same
key.

### Partly migrated on purpose

`button-group.tsx` is the one file that is not fully StyleX:

- **StyleX**: `ButtonGroup`'s own box (`display`, `width`, `align-items`, `flex-direction`, the
  `has-[>[data-slot=button-group]]:gap-2` rule, which is a condition on the group itself) and all
  of `ButtonGroupText`.
- **Tailwind**: the child-edge rules (`GROUP_CHILD_RULES` and `ORIENTATION_CHILD_RULES`), for the
  reason above. The `!` on `[&>[data-slot]:not(:has(~[data-slot]))]:rounded-{r,b}-lg!` is
  load-bearing and StyleX has no `!important`; the `button-group-text-last` case shows what it
  does (a button that is the last `[data-slot]` but not the last child keeps a rounded outer
  edge).
- **Untouched**: `ButtonGroupSeparator`. Every class there configures `Separator`, and its
  `bg-input` only reaches the element because `twMerge` deletes `Separator`'s own `bg-border`.
  A StyleX class would lose to `bg-border` instead — visibly, in dark, where `--border` is
  `oklch(1 0 0 / 10%)` and `--input` is `oklch(1 0 0 / 15%)`.

It finishes in PR 07 (`separator`), PR 05 (`input`) and PR 15 (`select`).

Measured with a headless-Chromium probe, not guessed. Both are a caller's Tailwind class
shadowing a **conditional** StyleX rule that `twMerge` used to leave alone — `twMerge` only
deletes a base class with the same variant key, so `text-muted-foreground` never removed
`hover:text-foreground`.

| Caller                                                                                 | Change                                                       | Restored by |

Two interaction tests drive them: `button variant states` (hover + focus per variant, the focused

hover in two variants, anchor badge focus, toggle focus, view-switch hover).

Three computed-style snapshots per theme:

- `computed-buttons-matrix-*.json` — every `[data-slot="button"]` in the section, 28 properties
  each: box, colour, radius, the composed `box-shadow`, `opacity`, `pointer-events`, transitions.
- `computed-badges-toggles-*.json` — the same for every badge and toggle.
- `computed-button-group-edges-*.json` — **every direct child** of 14 groups, with its four corner
  radii and four border widths. That is the only way to see the child-edge rules resolve against
  each other and against the button's own `in-data-[slot=button-group]:rounded-lg`; it is what
  proved the partly-Tailwind `ButtonGroup` renders identically.

The collector deliberately does **not** record `className`: the class list is the styling
mechanism, it changes by definition, and StyleX adds debug class names in dev that the production
build does not. (It did at first; the three snapshots were regenerated from the pre-migration
components once the field was dropped, before any component was migrated.)

## Built CSS

Production build compared against `55eb071`:

- **Tailwind portion: one rule added, none removed.** `.flex-shrink { flex-shrink: 1 }`, because
  `computed-styles.spec.ts` lists the CSS property name `flex-shrink` among the properties it
  snapshots and Tailwind's scanner reads every source file in the Vite root, `visual/` included.
  No element renders it. Kept over renaming the tracked property: the coverage is worth more than
  the 24 bytes, and PR 32 removes the utility layer entirely.
- Keeping the four `cva` strings byte-identical means Tailwind still emits every class they name,
  so nothing was dropped even though no component calls them any more.
- Six other rules appeared on the first build, each from a class-shaped token in a **comment**
  (`ring-3`, `ring-[3px]`, `ring-destructive/20`, `dark:ring-destructive/40`,
  `aria-invalid:ring-[3px]`, and a `rounded-r-lg` form). The comments were reworded until the diff
  was down to the one rule above — the hazard [`conventions.md`](conventions.md) warns about,
  seen twice now (PR 03 hit it with `mt-0`).
- **StyleX portion: 110 classes added, none removed.** The `priorityN` bucket assignment shifts
  again, which is order preserving (see [pr-03.md](pr-03.md#built-css)).
